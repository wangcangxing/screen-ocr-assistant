# 使用说明（OmniParser 增强版）

本工程 APK 的包名是 **`com.dsh.screenocr.omni`**，可与原 v1.3（`com.dsh.screenocr`）**并存安装**，互不影响。

> 适用对象：想「装好就能用」的使用者。接口字段与编号规则的权威定义见 [接口约定-SoM与解析服务.md](接口约定-SoM与解析服务.md)；逐个功能的实现改动、证据与未验证项见 [改造说明.md](改造说明.md)。

---

## 一、装 APK（PC 侧）

产物路径：`app\build\outputs\apk\debug\app-debug.apk`（只构建 debug；本工程没有 release 签名密钥，release 会退回 debug 签名，**不要发布**）。

```powershell
$env:JAVA_HOME='D:\JAVA\JAVA17'
& 'D:\Android\gradle\gradle-8.11.1\bin\gradle.bat' -p 'D:\program\screen-ocr-assistant-omniparser' assembleDebug
adb install -r -t 'D:\program\screen-ocr-assistant-omniparser\app\build\outputs\apk\debug\app-debug.apk'
```

确认装的是哪个包：

```powershell
adb shell pm list packages | Select-String 'com.dsh.screenocr'
# 期望看到 com.dsh.screenocr（原 v1.3）与 com.dsh.screenocr.omni（本改造版）两条
```

卸载本改造版（**会一并关掉它的无障碍开关，需要重新打开**）：

```powershell
adb uninstall com.dsh.screenocr.omni
```

## 二、打开无障碍

1. 打开应用 → 点「**打开无障碍设置**」。
2. 在系统列表里找到本应用（名称「屏幕答题助手」）→ 打开开关 → 允许。
3. 回到应用，状态区显示已连接即可。

实测提示：ColorOS 不允许用 adb 改无障碍开关（必须手动开），vivo / MuMu 允许；ColorOS / MIUI / vivo 常回收后台应用，建议把本应用加入「自启动 / 后台运行」白名单。

## 三、配大模型接口（必需）

1. 填「接口地址」（如 `https://api.deepseek.com/v1`）与「API Key」→ 点「保存配置」。
2. 点「**获取可用模型**」→ 从真实返回的列表里选一个（列表会标 `[可看图片]`、上下文长度、可用推理强度）。
3. 要让 **SoM 编号**起作用，必须选**带图片模态**的模型并**开启视觉模式**——编号是画在截图上的，纯文本模型看不到。
4. 也可先点「测试接口连通性」确认能通。

## 四、开关 SoM 编号标注

界面位置：配置页最下方「**SoM 编号标注与解析服务**」区。

| 控件 | 默认 | 说明 |
|---|---|---|
| 开关「SoM 编号标注（在截图上画编号框并附元素清单，模型回编号即可点准；关闭则回到 v1.3 行为）」 | **开**（`somEnabled=true`） | 开 = 截图贴编号框 + 附元素清单，模型可直接回编号（如 `B E7`）；关 = 完全回到 v1.3（不发标注图、不发清单、不解析编号） |
| 输入框「编号元素上限（默认 40，1~200）」 | `40`（`somMaxElements`，可填 1~200） | 元素太多时编号会挤、画面会乱；画面简单时可调小 |

- 编号是**本次截图本地重新编的**（E1、E2…，按从上到下、同一行从左到右），与解析服务返回的 `id` 不是同一套；模型只看应用给的编号。
- 开着 SoM 但本次**没有真把编号图发出去**（视觉模式关、标注失败等）时，应用**不附元素清单、也不认模型回的编号** —— 这是刻意设计（没图就没有编号依据）。

## 五、配解析服务（可选，默认关）

解析服务在 PC 上跑，手机连它有两种方式。**任一方式都要先在 PC 上把服务起起来。**

### 5.1 在 PC 上装依赖、下权重、启动

服务目录：`D:\program\screen-ocr-assistant-omniparser\omniparser-service`

```powershell
cd D:\program\screen-ocr-assistant-omniparser\omniparser-service

# 1) 建 venv。本机 PATH 上的 python 是 msys64 的、没有 pip —— 显式用 D:\Python312\python.exe
#    --system-site-packages 复用已装好的 CPU 版 torch（2.9.1+cpu，本机没有 CUDA）
D:\Python312\python.exe -m venv --system-site-packages .venv

# 2) 装依赖（文件名就是 requirements.txt；国内源实测可达，tuna 曾证书过期可换 mirrors.aliyun.com）
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 3) 下权重（约 1.4 GB；默认走 hf-mirror，失败自动回落官方站）
powershell -ExecutionPolicy Bypass -File .\download_weights.ps1

# 4) 启动服务，二选一（都监听 0.0.0.0）
#    a) 快速模式：跳过 Florence-2 图标描述，CPU 单张 ≈14.6s —— 手机端用这个
.\.venv\Scripts\python.exe server.py --backend lite --weights .\weights --device cpu --port 8011 --box-threshold 0.05 --no-caption

#    b) 全量图标语义：CPU 单张 ≈147.9s（60 个图标 × Florence-2），不适合手机端交互（见 5.4）
.\.venv\Scripts\python.exe server.py --backend lite --weights .\weights --device cpu --port 8010 --box-threshold 0.05 --caption-batch 16

#    c) 只验证链路（不需要权重，元素 label 一律带 mock- 前缀）
# .\.venv\Scripts\python.exe server.py --mock

# 5) 在 PC 本机自检（端口写你启动时用的那个）
Invoke-RestMethod 'http://127.0.0.1:8011/health'
```

期望 `/health` 返回 `ok=true`、`service=omniparser-service`、`mode=real|mock`、`backend=lite|upstream`、`device=cpu`；`real` 模式缺权重时服务会**直接退出（退出码 2）**并打印可复制的下载命令。
启动参数（都有默认值）：`--host 0.0.0.0`、`--port 8010`、`--backend lite|upstream`、`--mock`、`--weights ./weights`、`--device auto|cpu|cuda`、`--box-threshold 0.05`、`--caption-batch 32`、`--no-caption`、`--max-image-mb 12`。

**重启服务前先确认端口只有一个监听者**（Windows 的 `SO_REUSEADDR` 允许两个进程绑同一端口，会出现「端口在跑」但请求被两个实例分走、推理锁失效）：

```powershell
Get-NetTCPConnection -LocalPort 8011 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
```

### 5.2 手机怎么连（两种方式，任选其一）

> 应用里填的**端口必须与你启动的 `--port` 一致**。本文示例：快速模式 `8011`、全量模式 `8010`；只用一种即可。

**方式 A：局域网 IP**

1. PC 与手机连同一个 Wi-Fi / 同一网段。
2. PC 上查 IP：

```powershell
ipconfig
# 看当前在用网卡的 IPv4 地址，例如 192.168.1.23
```

3. 应用里「解析服务地址」填 `http://192.168.1.23:8011`（**换成你自己的 IP 与端口**，路径不用带）。
4. 首次连不上，多半是 Windows 防火墙拦了入站：放行该端口，或临时允许该 Python 进程通过防火墙。

**方式 B：adb reverse（走 USB，不受 Wi-Fi / 防火墙影响）**

```powershell
# 一个实例
adb reverse tcp:8011 tcp:8011
# 两个实例都映射（8010 全量 / 8011 快速）也可以各来一条
adb reverse tcp:8010 tcp:8010
adb reverse --list      # 应看到 tcp:8010 tcp:8010 与/或 tcp:8011 tcp:8011
```

应用里「解析服务地址」填 `http://127.0.0.1:8011`（端口对应反向映射的那个）。

- 需要 USB 连接且 `adb` 可用；**重插数据线、重启 adb、重启手机后要重新执行** `adb reverse`（映射会失效），否则会突然连不上。
- 这种方式下手机访问的 `127.0.0.1:<端口>` 就是 PC 上的同名端口，与方式 A 二选一即可，不要混填地址。

### 5.3 解析服务相关参数

界面位置：同上「SoM 编号标注与解析服务」区。

| 参数 | 默认 | 说明 |
|---|---|---|
| 开关「启用 OmniParser 解析服务（PC 侧，默认关；节点树/OCR 判不出题时用它兜底）」 | **关**（`omniParserEnabled=false`） | 关 = 完全不请求解析服务，行为与「服务不存在」一致 |
| 输入框「解析服务地址（HTTP，末尾不要带 /parse 或 /health）」 | **空**（`omniParserUrl=""`） | 例：`http://192.168.1.23:8011` 或 `http://127.0.0.1:8011` |
| 输入框「解析服务超时（毫秒，默认 4000）」 | **`4000` ms**（`omniParserTimeoutMs`，**可填 1000~60000**） | 单位毫秒。连快速模式（单张 ≈14.6s）建议设 `30000`；界面上限是 60000，配置导入也会被收敛到 60000 |

**失败纪律**：解析服务连不上 / 超时 / 返回非 2xx / 返回内容不合契约，都**不会中断答题流程**——只写日志，然后当作「没有这一路来源」继续；端侧节点树与 OCR 照常工作。失败后 **30s 内不再尝试**；同一屏 **30s 内复用上次解析结果**（0 元素也复用），不会每轮都重跑推理。

### 5.4 CPU 推理有多慢（重要）

本机全局 torch 是 `2.9.1+cpu`（**没有装 CUDA 版**），解析服务是纯 CPU 推理。实测同一张 1080×2400 真机截图（`shots\q2.png`）：

| 服务启动方式 | 单次 `/parse` | 手机端能不能用 |
|---|---|---|
| `--no-caption`（8011） | **≈14.6 秒**（14615 ms） | **能**：超时设 `30000` ms 就够 |
| 全量 caption（8010） | **≈147.9 秒**（147873 ms） | **不能**：单次已超过应用超时上限 60000 ms，每次都会在 60s 处超时被丢弃 |

所以：**手机端请连 `--no-caption` 实例（8011）**，并把「解析服务超时」设为 30000~60000 ms。要把全量图标语义接到手机端，只能先上 GPU（CUDA 版 torch + 支持 CUDA 的显卡）把单次压到 60s 以内；或把发图最长边调小以降低单次耗时。

首次请求还含模型加载 / easyocr 联网下模型（约 100 MB），会更慢：**先让 PC 侧手动打一次 `/parse` 预热**，再让手机连。

## 六、答完自动推进怎么用（v1.5，默认开）

界面位置：配置页「**答完自动推进（v1.5）**」区。

1. 开关「**答完自动推进（点下一题/滚动）**」默认**开**；关掉即完全不动页面（回到「答完就停」）。
2. 输入框「**连续推进上限（默认 3，1~10；连续这么多次仍没见到新题就暂停 60 秒）**」：填 `3` 表示最多连推 3 次就停 60 秒。页面很长、每次只能推进一点时填大些（如 5~8）；一页一题、点一下就该出新题时填小些（1~3）。

**它会做什么**

- 先点**屏幕里看得见**的「下一题 / 下一页 / 下页 / 下一节 / 下一讲 / 下一章 / 下一关 / 下一步 / 下一个 / 下一部分 / 继续下一题」按钮（`下一题(1/10)` 这种带括号/数字计数的也算；纯图标按钮靠 `contentDescription`）；
- 没有可点的按钮就**向下滚动**：先让页面自己滚（`ACTION_SCROLL_FORWARD`），不行再用上滑手势（画面位移约 0.7 屏）。

**什么时候不会推进（都不是故障）**

- 本次打开应用后**还没答过题** —— 防止在无关页面里乱翻；
- 距**最近一次作答**已超过 **60 秒** —— 答完一题最多自动推进 60s，避免在视频/长文档页无限滚动；
- 距上次推进不到 **4 秒**（冷却）；
- 滚动后画面没变化 → 判「到页尾」**暂停 60 秒**；连续推进达到上限（默认 3）也**暂停 60 秒**（新题一出现就清零；无效的节点滚动不计入）；
- 当前屏还有**要作答的题**（浮层里还亮着「提交作答」时**绝不**翻页）；
- 开着「试运行（只显示答案，不点击）」，或关着「启用屏幕处理」。

**误推进了怎么办**：把「答完自动推进」开关关掉即可（其它功能不受影响）；想更保守也可以把连续推进上限调成 1。

**怎么确认它在做什么**：日志里搜 `⑨ 推进：`，例如 `⑨ 推进：冷却中（距上次 2.2s < 4.0s）`、`⑨ 推进：已点「下一题」（坐标 181,1855）`、`⑨ 推进：本应用本次会话还没答过题，不推进`。

## 七、用「测试解析服务」按钮判断通不通

1. 配好地址、超时、`omniParserEnabled` → 点「**测试解析服务（GET /health）**」。
2. **它请求的是 `GET {地址}/health`**（不是 `/parse`），用你填的超时值。
3. **成功判据**：HTTP 2xx **且** 响应体 `ok=true`。表现：弹出「解析服务正常（<耗时>ms）」，日志出现
   `— GET http://…/health（超时 30000ms）—` 与 `— 解析服务正常：service=omniparser-service version=1.0 mode=real backend=lite（12ms）`，
   状态区显示「上次测试：正常（HTTP 200，mode=real，backend=lite，12ms）」。
4. **失败**：弹出「解析服务失败：<原因>」，日志是 `— 解析服务测试失败：<原因>`，状态区显示「上次测试失败：…」。地址没填时直接提示「请先填写解析服务地址」。

排查顺序（从最可能到最少见）：

1. PC 上 `Invoke-RestMethod 'http://127.0.0.1:8011/health'` 通不通？不通 → 服务没起来 / 起来就退出了（多为缺权重，退出码 2）。
2. 应用里的端口与启动的 `--port` 不一致（8010 vs 8011 最常见）。
3. 用方式 B 却忘了 `adb reverse tcp:8011 tcp:8011`（或重插线后没重跑）→ 重新执行。
4. 用方式 A 但 IP 变了（路由器重新分配）→ 重新 `ipconfig` 确认。
5. 防火墙拦入站端口 → 放行后重试。
6. 服务只监听了 `127.0.0.1` 而不是 `0.0.0.0` → 局域网方式连不上，用 `--host 0.0.0.0` 重启。
7. 端口被别的程序占用（或有两个进程都在听）→ 见第八节。

## 八、常见问题

**连不上（connection refused）**
- 服务没在跑，或启动了但立刻退出（`real` 模式缺权重会退出码 2）→ 看启动终端里的报错。
- 地址/端口写错：必须有 `http://` 和端口（如 `:8011`），不要带 `/parse`、`/health`；端口要与 `--port` 一致。
- 手机与 PC 不在同一网段（手机走了流量）→ 切回同一 Wi-Fi。

**超时**
- CPU 推理慢（见 5.4）：连 8011（`--no-caption`）把超时设 `30000` ms；**别把手机连到全量 caption 的 8010**（单次 148s 必然超时）。
- 首次请求含模型加载，先让 PC 侧手动打一次 `/parse` 预热。

**端口被占用 / 有两个进程在听**

```powershell
# 只看监听者（最准；<端口> 换成 8010 或 8011）
Get-NetTCPConnection -LocalPort 8011 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
# 或
netstat -ano | Select-String ':8011'
# 记下 OwningProcess（PID）后查看是谁：
Get-Process -Id <PID> | Select-Object Id,ProcessName,Path
```

**建议**：`Get-NetTCPConnection` 只应看到**一行**；出现多行说明有两个实例在听同一个端口（Windows 允许），请求会被分走、推理锁失效 → 先按 PID 清干净再起服务。换端口后**手机端地址要同步改**。

**服务返回 503**
- 契约定义 503 = 模型未就绪。`real` 模式下应先确保权重齐了再启动，不要「带伤运行」。

**服务返回 400 / 413**
- 400：请求体不是合法 JSON，或 `image_base64` 不是合法 base64 图片 —— 属于 APK 侧发送问题。
- 413：提交图片超过服务端上限（默认 12 MB）—— 把「发图最长边」调小。

**`python` 命令报没有 pip / 模块找不到**
- 本机 PATH 上的 `python` 是 msys64 的、没有 pip。**显式用 `D:\Python312\python.exe`**（见 5.1）。

**下载权重/依赖很慢或失败**
- 权重：`download_weights.ps1` 默认先走 `hf-mirror`，失败自动回落官方站（`hf-mirror` 的 `/resolve/` 现在会 308 跳转，`huggingface_hub` 不跟随，所以会先失败再回落，属正常）。
- pip 加镜像：`--index-url https://pypi.tuna.tsinghua.edu.cn/simple`（实测可达；tuna 若证书过期可换 `https://mirrors.aliyun.com/pypi/simple/`）。

**SoM 开了但模型还是给字母、不给编号**
- 视觉模式没开，或选的模型不能看图（编号只在图里）。
- 元素太多、框太小看不清 → 调小「编号元素上限」，或降低轮询频率避免连续截图。
- 模型本身不按协议回编号时，应用会自动退回原来的字母点击路径，不会因为 SoM 失效而卡住。

**装新包报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`**
- 说明手机上已有**同包名**的包但签名不同（如自行重打包过 `com.dsh.screenocr.omni`）→ `adb uninstall com.dsh.screenocr.omni` 后再装。
- 与 v1.3（`com.dsh.screenocr`）包名不同，**不会**因此冲突。

**开了自动推进但页面不动 / 乱翻页**
- 不动：先看日志里有没有 `⑨ 推进：`。`本应用本次会话还没答过题，不推进` → 正常（护栏，必须先答一题）；`距上次作答已 Ns（> 60s 窗口）` → 正常（窗口到期）；`暂停中（还有 Ns）` / `冷却中` → 正常（等它）。页面上确实没有「下一题」类按钮、也不可滚动时，它本来也无事可做。
- 乱翻：把「答完自动推进」关掉（见第六节）；它只在答过题之后、且限 60s 窗口内才会动。

**日志在哪**
- 应用内「运行日志」区（长按可复制）；命令行：`adb logcat -s ScreenOcr`。

## 九、出问题时要留的证据

1. 应用内运行日志（或 `adb logcat -s ScreenOcr` 的输出）。
2. PC 侧服务终端的完整输出，含启动参数与报错。
3. `Invoke-RestMethod 'http://127.0.0.1:<端口>/health'` 的返回。
4. 手机型号 / Android 版本 / 分辨率，以及「解析服务地址」的填法（方式 A 还是 B、端口是 8010 还是 8011）。

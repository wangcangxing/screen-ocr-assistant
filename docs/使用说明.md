# 使用说明（v1.4 · OmniParser 增强已并入主线）

本工程就是 `screen-ocr-assistant` **主线**（包名 **`com.dsh.screenocr`**）。v1.4 起，
原先独立的 `screen-ocr-assistant-omniparser`（`com.dsh.screenocr.omni`）的全部能力已合并回来，
**不再有第二个包**。

> - 接口字段与编号规则的权威定义：[接口约定-SoM与解析服务.md](接口约定-SoM与解析服务.md)
> - 逐个功能的实现改动、证据与未验证项：[改造说明.md](改造说明.md)
> - 本工程根目录的 `执行报告-变更记录-*.md` 是按时间归档的逐轮改动与真机证据（不入库）。

⚠️ **升级注意**：签名密钥沿用本工程的 `keystore/screenocr-release.jks`，所以**原 v1.3 用户可原地升级**；
但**曾装过 `com.dsh.screenocr.omni`（独立密钥）的机器必须先卸载再装**（签名不同，无法覆盖安装）。

---

## 一、装 APK（PC 侧）

```powershell
$env:JAVA_HOME='D:\JAVA\JAVA17'
& 'D:\Android\gradle\gradle-8.11.1\bin\gradle.bat' -p 'D:\program\screen-ocr-assistant' assembleDebug
adb install -r -t 'D:\program\screen-ocr-assistant\app\build\outputs\apk\debug\app-debug.apk'
```

- 产物：`app\build\outputs\apk\debug\app-debug.apk`
- **release 签名**：`local.properties` 里配了 `release.storeFile` 时 `assembleRelease` 会用它签名
  （官方指纹 `8d09734c…6aa7`）；**没有配就退回 debug 签名**，那种产物不要对外发布。
- 确认装在哪个包：

```powershell
adb shell pm list packages | Select-String 'com.dsh.screenocr'
# 期望：com.dsh.screenocr（本工程）。若还有 com.dsh.screenocr.omni，说明旧独立版没卸干净。
```

- 卸载（**会一并关掉无障碍开关，需重新打开**）：

```powershell
adb uninstall com.dsh.screenocr
```

## 二、打开无障碍

1. 打开应用 → 主页面点「**打开无障碍设置**」。
2. 系统列表里找到本应用（名称「屏幕答题助手」）→ 打开开关 → 允许。
3. 回到应用，主页面状态区显示「无障碍服务：已连接 ✅」即可。

实测提示：ColorOS 不允许用 adb 改无障碍开关（必须手动开），vivo / MuMu 允许；
ColorOS / MIUI / vivo 常回收后台应用，建议把本应用加入「自启动 / 后台运行」白名单。

## 三、两页界面（v1.4 拆页）

v1.4 把配置拆成两页，**主页面只留每天要动的东西**：

| 页面 | 内容 |
|---|---|
| **主页面** | 运行状态（只读，每 1.5s 刷新）、「打开无障碍设置」、行为与触发（屏幕处理 / 自动点击 / 试运行）、**SoM 编号标注开关**、**答完自动下一题**（开关 + 连续推进上限）、**答题自动提交**（三选一）、「高级设置」入口 |
| **高级设置**（主页最下方进入） | 大模型接口（地址 / Key / 模型列表 / 推理强度 / 系统提示词 / 视觉模式）、识别与触发参数（发图最长边 / 轮询 / OCR 缩放 / 判题阈值 / 去抖 / 置信度 / 去重 / 超时）、SoM 元素上限、解析服务（开关 / 地址 / 超时 / 测试）、运行日志 |

**开关是「一拨即存」的**（不需要再点保存）；文本框仍要点「保存配置」。
> 这条是修出来的：拆页后「保存配置」在设置页顶部、开关在底部，早期版本下拨开关不会落盘、还会被读回弹回原状。

## 四、配大模型接口（必需）

在**高级设置**页：

1. 填「接口地址」（如 `https://api.deepseek.com/v1`）与「API Key」→ 点「**保存配置**」。
2. 点「**获取可用模型**」→ 从真实返回的列表里选一个（列表会标 `[可看图片]`、上下文长度、可用推理强度）。
3. 要让 **SoM 编号**起作用，必须选**带图片模态**的模型并**开启视觉模式** —— 编号是画在截图上的，纯文本模型看不到。
4. 也可先点「测试接口连通性」确认能通。

## 五、SoM 编号标注

- 开关在**主页面**「SoM 编号标注与解析服务」区；「编号元素上限」在**高级设置**页（默认 40，1~200）。

| 控件 | 默认 | 说明 |
|---|---|---|
| 「SoM 编号标注」开关 | **开**（`som_enabled=true`） | 开 = 截图贴编号框 + 附元素清单，模型可直接回编号（如 `B E7`）；关 = 回到 v1.3（不发标注图、不发清单、不解析编号） |
| 「编号元素上限」 | `40`（`som_max_elements`） | 元素太多时编号会挤；画面简单时可调小 |

- 编号是**本次截图本地重新编的**（E1、E2…，按从上到下、同一行从左到右），与解析服务返回的 `id` 不是同一套。
- 开着 SoM 但本次**没有真把编号图发出去**（视觉模式关、标注失败等）时，应用**不附元素清单、也不认模型回的编号** —— 这是刻意设计（没图就没有编号依据）。

## 六、配解析服务（PC 侧，可选，默认关）

解析服务在 PC 上跑，手机连它有两种方式。**任一方式都要先在 PC 上把服务起起来。**

### 6.1 在 PC 上装依赖、下权重、启动

服务目录：`D:\program\screen-ocr-assistant\omniparser-service`

```powershell
cd D:\program\screen-ocr-assistant\omniparser-service

# 1) 建 venv。本机 PATH 上的 python 是 msys64 的、没有 pip —— 显式用 D:\Python312\python.exe
#    --system-site-packages 复用已装好的 CPU 版 torch（2.9.1+cpu，本机没有 CUDA）
D:\Python312\python.exe -m venv --system-site-packages .venv

# 2) 装依赖（国内源实测可达；tuna 曾证书过期可换 mirrors.aliyun.com）
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 3) 下权重（约 1.4 GB；默认走 hf-mirror，失败自动回落官方站）
powershell -ExecutionPolicy Bypass -File .\download_weights.ps1

# 4) 启动服务，二选一（都监听 0.0.0.0）
#    a) 快速模式：跳过 Florence-2 图标描述，CPU 单张 ≈14.6s —— 手机端用这个
.\.venv\Scripts\python.exe server.py --backend lite --weights .\weights --device cpu --port 8011 --box-threshold 0.05 --no-caption

#    b) 全量图标语义：CPU 单张 ≈147.9s，不适合手机端交互（见 6.4）
.\.venv\Scripts\python.exe server.py --backend lite --weights .\weights --device cpu --port 8010 --box-threshold 0.05 --caption-batch 16

#    c) 只验证链路（不需要权重，元素 label 一律带 mock- 前缀）
# .\.venv\Scripts\python.exe server.py --mock

# 5) 在 PC 本机自检
Invoke-RestMethod 'http://127.0.0.1:8011/health'
```

期望 `/health` 返回 `ok=true`、`service=omniparser-service`、`mode=real|mock`、`backend=lite|upstream`、`device=cpu`；
`real` 模式缺权重时服务会**直接退出（退出码 2）**并打印可复制的下载命令。

**重启服务前先确认端口只有一个监听者**（Windows 的 `SO_REUSEADDR` 允许两个进程绑同一端口，
会出现「端口在跑」但请求被两个实例分走、推理锁失效）：

```powershell
Get-NetTCPConnection -LocalPort 8011 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
```

### 6.2 手机怎么连（两种方式，任选其一）

> 应用里填的**端口必须与你启动的 `--port` 一致**。本文示例：快速模式 `8011`、全量模式 `8010`。

**方式 A：局域网 IP** — PC 与手机同一 Wi-Fi → `ipconfig` 查当前网卡 IPv4 → 应用里填 `http://192.168.1.23:8011`。
首次连不上多半是 Windows 防火墙拦入站。

**方式 B：adb reverse（走 USB，不受 Wi-Fi / 防火墙影响）**

```powershell
adb reverse tcp:8011 tcp:8011
adb reverse --list
```

应用里填 `http://127.0.0.1:8011`。
**重插数据线、重启 adb、重启手机后映射会失效**，要重新执行。

### 6.3 解析服务相关参数（在**高级设置**页）

| 参数 | 默认 | 说明 |
|---|---|---|
| 「启用 OmniParser 解析服务」开关 | **关**（`omni_parser_enabled=false`） | 关 = 完全不请求解析服务 |
| 「解析服务地址」 | **空**（`omni_parser_url`） | 例：`http://192.168.1.23:8011`；**末尾不要带 `/parse` 或 `/health`** |
| 「解析服务超时」 | **`4000` ms**（`omni_parser_timeout_ms`，1000~60000） | 连快速模式（单张 ≈14.6s）**建议设 `30000`** |

**失败纪律**：连不上 / 超时 / 非 2xx / 内容不合契约，都**不会中断答题流程** —— 只写日志，然后当作
「没有这一路来源」继续。失败后 **30s 内不再尝试**；同一屏 **30s 内复用上次解析结果**。

### 6.4 CPU 推理有多慢（重要）

本机全局 torch 是 `2.9.1+cpu`（无 CUDA），纯 CPU 推理。实测同一张 1080×2400 真机截图：

| 启动方式 | 单次 `/parse` | 手机端能不能用 |
|---|---|---|
| `--no-caption`（8011） | **≈14.6 秒** | **能**：超时设 `30000` ms 就够 |
| 全量 caption（8010） | **≈147.9 秒** | **不能**：超过应用超时上限 60000 ms，每次都被丢弃 |

首次请求还含模型加载 / easyocr 联网下模型（约 100 MB），建议**先在 PC 侧手动打一次 `/parse` 预热**。

## 七、用「测试解析服务」按钮判断通不通

高级设置页点「**测试解析服务（GET /health）**」：

- 它请求的是 **`GET {地址}/health`**（不是 `/parse`），用你填的超时值。
- **成功**：HTTP 2xx **且** 响应体 `ok=true` → 弹「解析服务正常（<耗时>ms）」，状态区显示「上次测试：正常（…）」。
- **失败**：弹「解析服务失败：<原因>」；地址没填时直接提示「请先填写解析服务地址」。

排查顺序：① PC 上 `/health` 通不通（不通 → 服务没起来或缺权重退出）→ ② 端口不一致（8010 vs 8011）
→ ③ 方式 B 忘了 `adb reverse` → ④ IP 变了 → ⑤ 防火墙 → ⑥ 服务只听 `127.0.0.1` → ⑦ 端口被两个进程占。

## 八、答完自动下一题（默认开）

- 开关与「连续推进上限」都在**主页面**「答完自动推进」区。
- **它会做什么**：先点屏幕上**看得见**的「下一题 / 下一页 / 下一节 / 下一步…」按钮
  （`下一题(1/10)` 这种带计数的也算）；没有可点的按钮就**向下滚动**（先 `ACTION_SCROLL_FORWARD`，不行再上滑手势）。
- **什么时候不会推进（都不是故障）**：本次打开应用后还没答过题；距最近一次作答超过 **60 秒**；
  距上次推进不到 **4 秒**；滚动后画面没变化 → 暂停 60 秒；连续推进达上限 → 暂停 60 秒；
  当前屏还有要作答的题；开着试运行或关着屏幕处理。
- **确认它在做什么**：日志搜 `⑨ 推进：`。
- **误推进了怎么办**：关掉这个开关；或把上限调成 1。

## 九、答题完毕收尾：自动提交 / 停手（v1.4 起用**题号**判定）

主页面「答题完毕收尾」三选一：

| 选项 | 行为 |
|---|---|
| 什么都不做（默认） | 保持旧行为，不做任何收尾 |
| **直接提交** | 自动点「提交作业」+ 确认弹窗里的「确认」 |
| **继续答题（停手）** | 整卷完成后停手，不再操作本应用（等同退出） |

**怎么判断"整卷完成"（v1.4 改版，不靠 App 自己记账）**：

1. 识别到卷面标题（如「第十章单元测试」）后，先点开**题卡**读一遍题号，取**最大题号**当总题数 `N`；
2. 之后用**当前题号**判定：`题号 < N` → 继续作答并推进；`题号 == N` → 进入收尾；
3. 收尾前再确认**最后一题确实处理过**（在去重记录里）—— 因为平台读不到每题的作答标记，
   只看题号相等会在最后一题还没答时就交卷。

**它不会做的事（都是刻意的）**：读不到「提交作业」按钮 **或** 读不到确认按钮 → **放弃提交**（宁可不交）；
试运行模式下只打印「本应提交」。

**怎么确认它在做什么**：日志搜 `⑩`，例如
`⑩ 收尾：题号明细（5 个纯数字节点）：1,2,3,4,5`、
`⑩ 进度：本卷总题数 N=5（取题卡最大题号），当前第 5 题 → 已在最后一题`、
`⑩ 收尾：已到最后题且已处理（题号 5/5）→ 执行收尾`、
`⑩ 收尾：已点「提交作业」…` → `⑩ 收尾：已点「确认提交」…`。

**换卷自动继续**：同一 App 内手动换到另一份卷时，只要**卷面标题变了**，停手状态会自动解除并按新卷继续答题。

## 十、题目太长、超出页面怎么办

v1.4 起自动处理：题干或选项超出屏幕时，**先在页内滚动把题面读全**（每道题最多 2 次），再作答与点击。
日志搜 `⑨ 长题：`。

## 十一、常见问题

**装新包报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`**
- 说明已有同包名但签名不同的包（例如旧的 `com.dsh.screenocr.omni`，或自行重打过包）→ 先 `adb uninstall` 再装。

**无障碍自己断了 / 应用没反应**
- 看状态区「无障碍服务」是否已连接；部分 OEM 会在后台回收，加入自启动白名单。
- 服务在答题中途解绑时，本轮作答会被放弃（日志：`大模型返回时无障碍服务已不在`），下一轮会重来。

**答完却不提交**
- 先看日志有没有 `⑩ 进度：本卷总题数 N=…`。**没有 N** 说明题卡没读到题号（先确认屏幕上能手动打开「题卡」）。
- 有 N 但一直「尚未答完」：说明它认为最后一题还没处理过，或当前题号还没到 N。
- 日志里若出现 `题卡校验冷却中`，是"面板状态异常"的自我保护，最长 15 秒，会自动恢复。

**开了自动推进但页面不动 / 乱翻页**：见第八节。

**日志在哪**：高级设置页底部「运行日志」（长按复制全部）；命令行 `adb logcat -s ScreenOcr`。

## 十二、出问题时要留的证据

1. 应用内运行日志（或 `adb logcat -s ScreenOcr` 全文，**建议连 `DEDUP#` / `MARK#` / `⑩` / `⑨ 长题` 一起留**）。
2. PC 侧服务终端的完整输出（含启动参数与报错）；`Invoke-RestMethod 'http://127.0.0.1:<端口>/health'` 的返回。
3. 手机型号 / Android 版本 / 分辨率；解析服务地址的填法（方式 A 还是 B、端口是 8010 还是 8011）。
4. 出问题时**屏幕截图**或 `adb shell uiautomator dump`（用于判断题号、选项与面板状态）。

## 1. 为什么改

原 v1.3 的链路是「节点树/OCR → 文字 → 大模型回选项字母 → 本地在节点/框里找回可点目标」，有三个它解决不了的场景：

1. **WebView 里的选项 `clickable=false`**：找到文本也点不中（`ACTION_CLICK` 无效，只能坐标点击，而坐标又依赖 OCR 框精度）。
2. **图标认不出来**：端侧 ML Kit 只有文字 OCR，没有图标语义；「返回/关闭/× 」这类按钮只能靠猜。
3. **节点树与 OCR 都读不到题时没有第三路来源**：视频/Canvas 画面只有一种来源兜底。
4. **（v1.5 追加需求）答完一题后页面不动**：题做完还得人工翻页/往下滚，长页面里的下一题与「下一题」按钮正好都压在折叠线以下 —— 原版无从下手。

改造给出三条**加法**（都可关闭）：

- **端侧 SoM 编号标注**：把候选点击元素画成带编号的框贴进截图，并把「编号 → 元素」清单随消息发给多模态模型，让模型直接**回编号**；点击时优先用该编号对应框的中心。这样「点得准」不再依赖本地找回目标的能力。
- **PC 侧 OmniParser 解析服务**：手机 POST 截图，拿回结构化元素（YOLO 图标检测 + Florence-2 图标语义 + easyocr 文字框）。它既是**识别源③**（判题兜底），也是 SoM 的**图标元素来源**（端侧拿不到的语义）。
- **答完自动推进（v1.5）**：当前屏没有仍需作答的**可见**题目时，先点可见的「下一题/下一页…」，没有可点的按钮才向下滚动（详见 §7、契约 §6）。

原工程 `D:\program\screen-ocr-assistant\` **一个字节都没改**（契约 §5）；本改造在同级新目录 `D:\program\screen-ocr-assistant-omniparser\`，靠 `applicationId` 不同做到两个版本并存安装。

## 3. SoM 编号与提示词协议怎么落地（对照契约章节）

### 3.1 元素合并与编号（契约 §2.1）

- **来源优先级 = 候选加入顺序**（`assembleSomElements`，契约 §2.1）：① `node`（`NodeReader.toOcrResult(allWindowRoots(), …)` **当场重读一遍**节点树，取此刻坐标）→ ② `ocr`（仅当本轮结果真的来自截图 OCR 时才把 OCR 行算作候选，坐标过 `scaleToScreen(res, box)` 换回屏幕坐标）→ ③ `omniparser`（`Element.screenBox()` 优先用 `bbox_ratio × 屏幕尺寸`，ratio 不合法才退回 `bbox_px` 按提交图尺寸缩放）。
- **去重先到先得**（`SomElement.merge` + `overlaps`）：`IoU > 0.6` **或**「存在包含关系且面积差 < 4 倍」判为同一个；容器比子元素大 ≥4 倍时**两个都保留**（v1.1 修「大框吞小框」）。
- **丢弃**：任一边 <8px；面积 > 屏幕 60%；与已保留元素重叠。
- **上限**：`prefs.somMaxElements`（默认 40，界面/配置 `coerceIn(1,200)`），保序截断。
- **编号**：`centerY` 分桶 30px 内视为同一行，行内按 `left`，重新编 `E1..EN`。
- **编号是 APK 自己重编的**，与服务端 `elements[].id` **不是同一套**（契约 §2 开头）：真机日志里模型回的 `E12` 就是 APK 的编号。

### 3.2 发给模型的清单（契约 §2.2）

`LlmClient.buildUserContent`：`【屏幕文字】` → `【界面元素（对应图中编号的框）】`（`E1 文本 关闭` 逐行）→ `【题干】` → `【选项】`。**清单紧跟屏幕文字之后**，与契约 §2.2 一致；`SomElement.describe()` 负责行格式。

### 3.3 模型回复协议（契约 §2.3）

- 提示词升 v3：`...可在字母后追加一个空格和该编号（例如 B E7）`，保留 `NONE` 出口与「只输出这一小段」的纪律。
- `parseAnswer`：JSON 读 `element_id`（容忍 `"E7"` 字符串写法）；纯文本用正则 `(?:^|[^A-Za-z0-9_])(?:[Ee]|元素|#|＃)\s*([1-9][0-9]*)` 认 `E7`/`元素7`/`#7`，**取第一个命中，解析不出即 null，绝不猜**。
- **向后兼容**：老格式（只有字母、JSON 不带 `element_id`）结果与 v1.3 完全一致，只是 `elementId` 为 null；`allowElementId=false` 时连解析都不做。

### 3.4 点击优先级与反矛盾保护（契约 §2.4）

- 优先级：① 模型给的编号能在**本轮** SoM 清单里找到 → 用该框中心 → ② 退回 `ClickPlanner.plans`（节点文本 → 可点祖先 → OCR 框中心）→ ③ 都没有 → 不点（保留 v1.3「宁可不点」纪律）。
- **不是新写一套点击**：SoM 路径生成的是同一个 `ClickPlan`，最终仍走 `performPlan → clickAtPoint → (findDeepestAt / findClickableAt / rootTap) → tapAt`（验证报告 §6.1）。
- 反矛盾保护（v1.1 判据）：`conflictsWithAnswerLetter` 用 `TextMatch.optionTokenOf(label)` 抽归属标记 —— **长标签参与判定**（不再受 `normalizeLabel` 的 12 字截断影响）、中文单字与图标描述抽不出标记故不算矛盾、**只在同一标记族内比较**（字母对字母、数字对数字）。判为矛盾则不点编号、退回 ClickPlanner 并打警告。

### 3.5 降级与失败纪律（契约 §3）

| 场景 | 行为 |
|---|---|
| 解析服务连不上/超时/非 2xx/JSON 不合契约 | 记日志、`ok=false`、**按「没有它」继续**；并**退避 30s**（`OMNI_FAILURE_COOLDOWN_MS`）不再尝试，避免每轮白等一个 `omniParserTimeoutMs` |
| 同屏 30s 内已成功解析过 | 复用缓存（键 = 屏幕指纹 + 图宽高 + `somMaxElements`），不再发 HTTP；**0 元素也缓存**（那也是一次昂贵推理）。只缓存成功，失败不进缓存 |
| `somEnabled=false` | 不组装元素、不发清单、不解析编号，行为回到 v1.3 |
| `omniParserEnabled=false`（默认） | 完全不请求解析服务，与「服务不存在」等价 |
| **`sendScreenshot=false`**（v1.1 §3 硬规矩） | **任何路径都不得把截图发给大模型**：`dispatchLlm` 在唯一出口再兜一道 `jpegToSend = if (sendScreenshot) jpeg else null`；解析服务要用的那张 JPEG 只喂 `POST /parse` |
| 有图才认编号（P2 决策） | `listSent = annotated != null && imageSent`，`allowElementId = somElements.isNotEmpty()` —— 没真发编号图时**不附清单、不认编号**，编号这条路径整体不存在 |

### 3.6 识别源③怎么用

`rebuildFromOmniText` 把解析服务的 **text 元素**重建成 `OcrResult` 再判一次，但**只在本地「不像题目」或「没有选项」时**才做（`needRebuild = !q0.isCandidate || q0.options.isEmpty()`）：本地已判出题目时，解析服务只用来补 SoM 元素，不覆盖本地判定。

## 4. 完整优先级链（识别与点击）

```
识别：① 无障碍节点树（NodeReader，文本/坐标最准）
   → ② 端侧 ML Kit OCR（节点树读不到或判不出题时）
   → ③ 解析服务文字元素（仅当 ①② 判不出题或没有选项，且服务可用）

点击（拿到模型答案后）：
  ① 模型编号 elementId → 本轮 SoM 清单命中 → 该框中心（先过反矛盾保护）
  ② ClickPlanner：节点文本匹配 → 可点祖先 ACTION_CLICK → OCR 框中心
  ③ 都不行 → 不点（打日志「宁可不点」）
```

## 5. 解析服务：两种后端与性能实测

来自 `omniparser-service/README.md` §7（T2 自跑，产物在 `omniparser-service/run/`，不入库）：

| 模式 | 单次 `/parse` `elapsed_ms` | 元素数 | 备注 |
|---|---|---|---|
| `--mock` | 0 | 4（label 前缀 `mock-`） | 不加载模型、不需要权重；契约自检 93/93 通过 |
| `real + lite + cpu + --no-caption` | **14615（≈14.6 s）** | **83 = 23 text + 60 icon** | `shots\q2.png` 1080×2400；easyocr ≈11.7 s + YOLO ≈1.9 s |
| `real + lite + cpu + 全量 caption` | **147873（≈148 s）** | 83 = 23 text + 60 icon | 60 个图标 × Florence-2；CPU 上这就是上限 |
| `real + lite + cpu + --no-caption`（`quiz.png`） | 17142（≈17.1 s） | 80 | annotate 缺省 false → 响应无 `som_image_base64` |

- **只有 `lite` 后端被验证**；`--backend upstream` 需要 paddleocr 等上游全量依赖，**未验证**（诚实清单）。

## 7. 答完自动推进（v1.5 / T7）

> 需求原话：「加入滚动功能，当当前页面题目已全部完成后，自动翻页或者点击下一题」。
> 口径的唯一来源是契约 **§6**（v1.2 新增，v1.2.1 词表规则、v1.2.2 推进窗口与「非题目屏幕也要能推进」）。

### 7.1 判定口径：什么时候允许推进

「当前页题目已全部完成」= 当前屏**没有仍需作答的可见题目**。两条路径都要覆盖（契约 §6.1）：

1. **`!q.isCandidate`**（整屏不像题目）→ 两处早返回分支都**先调度推进再 return**：
   - `onOcr` 的 `!q.isCandidate && !omniAvailable`（解析服务默认关闭时最常走的路径）；
   - `afterShotEncoded` 里解析服务兜底判题后仍非题目。
2. **去重命中且已答成**：既有「刚答过 → 只补收尾、不重复作答」的那一刻，`submitState()` 为 `DONE` 或 `UNKNOWN` → 同样调度推进。

**仍为 `PENDING`（还亮着「提交作答」）时绝不推进**：两个 PENDING 分支都打 `⑨ 推进：当前屏仍有未作答题目，不推进` 并 return。

> **这一条是修出来的（D-d）**：v1.2/v1.2.1 把「屏幕不是题目」在原 `if (!q.isCandidate && !omniAvailable) return` 里直接 `return` 掉了，于是「题目全做完 → 页面没题了 → 翻页」这条**主路径在解析服务默认关闭时永远不可达**（真机：滚进无题区后推进永久停住）。修法就是「无事可做也要先问一句本轮还需不需要推进」。

### 7.2 可见性（安全底线，契约 §6.2）

`isVisibleOnScreen(box, w, h)`：框与 `Rect(0, 0, 截图宽, 截图高)` **相交且面积 > 0**（贴边零重叠算不可见；`w/h<=0` 直接 false）。

- **推进按钮**只接受可见节点（`findVisibleAdvanceTarget` 逐个过滤）；
- **点击 / 编号目标**在屏幕外 → **不点它**，也**不退回 ClickPlanner**（否则「屏幕外点不到」会被兜底掩盖成「点了别的目标」），而是打印 `⑨ 推进：目标在屏幕外，先滚动把它带进来` 并转为滚动带进来；多选时只丢掉屏幕外的计划、屏幕内的照点（`offScreenPlans`）。

### 7.3 动作优先级：先点按钮，没有才滚动（契约 §6.3）

1. **点可见的推进按钮**：`NodeReader.findTextNodesBy(allWindowRoots(), predicate)` 找节点 → `clickAtPoint(box.centerX(), box.centerY(), "推进")`（**复用既有点击**：最深叶子 `ACTION_CLICK` → 可点节点 → 坐标手势，没有第二套）→ 成功打 `⑨ 推进：已点「下一题」（坐标 x,y）`。
2. **没有可见按钮 → 向下滚动**：`⑨ 推进：当前屏没有可见的推进按钮，改为向下滚动`
   - 先试 `ACTION_SCROLL_FORWARD`：`findScrollableNode` 取**可见且可滚动、面积最大**（同面积取更深）的节点 → 成功打 `⑨ 推进：可滚动节点 ACTION_SCROLL_FORWARD 成功`；
   - 否则上滑手势：`(w/2±10, 0.85h±10) → (w/2±10, 0.15h±10)`，300ms，落点 ±10px 抖动 → `⑨ 推进：改用上滑手势（x1,y1 → x2,y2）`；
   - 反向（目标在屏幕上方）用 `ACTION_SCROLL_BACKWARD` / 下滑手势。

> ⚠️ **契约 §6.3 与实现不一致，以代码为准**：契约写的手势是 `(w/2, h*0.78) → (w/2, h*0.78 - h*0.5)`（位移半屏），实现在 F5 之后是 **`0.85h → 0.15h`**（位移约 0.7 屏）。契约文字是 v1.2.1 初版口径，改动由 Lead 判定并已落码，但**契约原文尚未同步** —— 复核时别用 §6.3 的数字断言代码错了。

### 7.4 词表与匹配规则（契约 §6.4）

关键词（**按长度从长到短**排序，多命中取最长）：`继续下一题`、`下一部分`、`下一题`、`下一页`、`下页`、`下一节`、`下一讲`、`下一章`、`下一关`、`下一步`、`下一个`。
**故意不含裸「继续」**：它已在收尾的「关闭」词表里（继续观看/继续播放/继续），两处都用会把关闭浮层当成推进。

判定（`advanceLabelOf`）= `trim` → **先删掉成对括号整段**（`BRACKET_GROUP`：`（…）(…)【…】[…]《…》〈…〉«…»`）→ 必须**以某关键词开头** → **余下每个字符都在装饰白名单内**（25 个 `Unicode White_Space` 码点 + 半角/全角数字 `0-9０-９` + `。.、,，!！?？:：;；<>》»→›~～-—–·•*×|/／`）；只要还剩中文/字母等实义字符就不命中。
节点文本取 `text`，**空/全空白才退回 `contentDescription`**（纯图标按钮只有后者）。

- 命中示例：`下一题`、`下一题。`、`下一题 >`、`下一题(1/10)`、`下一题 ３/10`、`下一关【第2关】`、`继续下一题`、` 下一题 `；
- 不命中：`下一题练习`、`下一题目`、`下一步骤`、`点击下一题`（前缀不符）、`上一题`、`继续`、`继续观看`、`Next`（大小写敏感）。

### 7.9 已知限制与未验证（本功能）

1. **推进只在「答过题之后」生效**（`answeredThisSession>0` + 60s 窗口），**不能当通用滚动器**用；在没答过题的页面（纯浏览/视频）永远不会推进。
2. **`/quiz-long`（2200px 空白的人造极端夹具）未完全验证**：超过一屏的空白区内无法把第 2 题带进视野，最终按「手势无位移 → 暂停 / 60s 窗口到期」停下。判定为**夹具不真实 + Chrome a11y 懒加载**，不算功能缺陷，但确实没跑通。对照：`/quiz-near`（第 2 题就在折叠线下方一点、700px 空白）**跑通了**。
3. **契约 §6.3 的手势几何与实现不一致**（见 §7.3），复核时以代码为准。
4. **设备覆盖**：真机验收只在 MuMu 模拟器（`emulator-5554`，Android 12）；无真机、无 Android 13/14/15。
5. **T8 的结论一律是「代码级」**：`BRACKET_GROUP` 正则本身仍走 ICU 引擎，静态检查只能排除已知 P0/P1，实际识别效果以真机日志为准；差分 131 通过 / 0 不通过 / 差异 2（2 条差异是 Lead 认可的「括号剥离先于前缀判定」的有界放宽）。
6. **`findScrollableNode` 面积优先**：可能选中不覆盖题目区域的滚动容器；T8 判定为「实现选择、低风险」，且 F5 的手势兜底把它限制在一轮之内。

## 9. 已知瑕疵、未完成项与升级触发条件

**判定为可接受、保持现状**

1. **30px 分桶会让编号顺序出现「下排左」在「上排右」之前**（契约 §2.1 字面行为：先按 `centerY` 排序，行首 `centerY` 差 ≤30px 视为同一行，再行内按 `left`）。影响有限：编号徽标画在各自框上，模型看图能对上；只是**清单顺序**与视觉上下顺序可能不一致。Lead 判定为可接受，**不修**（验证报告 §5.1 反例 B）。
2. **同一段文本可能出现两个编号**：多行节点框（500×200）与单行 OCR 框（480×40）面积差 5.2 倍 >4 倍 → 两者都保留（验证报告 §10 H1）。点哪个都落在同一区域、不会点错，代价是清单变长、更早撞 `somMaxElements=40`。
3. **F4 缓存键不含解析服务 URL**：30s 内切换地址可能复用旧结果（已知取舍，契约外实现细节）。
4. **契约 §6.3 的手势几何落后于实现**（`0.78h→0.28h` vs 代码 `0.85h→0.15h`）：本节以代码为准，契约原文待 Lead 同步（见 §7.3）。
5. **`/quiz-long` 夹具未跑通**：2200px 空白区无法被带进视野，属夹具不真实（见 §7.9 第 2 条）。

**未完成 / 未验证（诚实清单）**

1. **只在一台模拟器上做过端到端验收**（MuMu `emulator-5554`，Android 12）：没有真机，也没有 Android 13/14/15 的实测。原工程已验证 Android 11/16 真机，本改造未在这些设备复跑。
2. **`--backend upstream` 未验证**（缺 paddleocr 等上游全量依赖）。
3. **MuMu 上 `takeScreenshot` 返回黑图**（原工程坑点 #35）：本模拟器上编号图只有编号、没有画面内容，发给解析服务也恒定 0 元素；**真机不受影响**（对照实验：关 SoM 发原图同样全黑 → `tools/acceptance-out/pure-black-900x1600.jpg`）。
4. **CPU 下全量 caption 约 2.5 分钟/张**，是客观上限；要交互式必须 `--no-caption` 或上 GPU。
5. **Android 侧没有 JVM 单测环境**：SoM 合并/画框这些 Android 依赖代码无法在 ART 之外执行；验证靠「逐字复制源码 + 真实 `kotlinc` 编译运行」（验证报告 §5/§9/§10）+ 真机日志。
6. **easyocr 是英文模型**：中文界面会出 `H03 GG1l`、`#Awito` 这类误识别，按契约原样返回、未美化；中文文本仍以端侧 OCR/节点树为准。

**后续升级的触发条件（到点再做，现在不做）**

1. 有**真机 + GPU**：把解析服务切到 CUDA 版 torch，才能开全量 caption 交互使用；同时补 Android 13/14/15 的设备矩阵。
2. 若真机上也出现「容器框吞选项」或同文本重复编号影响使用：再收紧 `overlaps`（例如给「同文本高重合框」加判据）——需要同时改契约 §2.1 与 Android 侧。
3. 若用户要在 30s 内来回切换解析服务地址：把 URL 加进缓存键。
4. 要发布产物之前：补 release 签名密钥（本工程 `keystore/` + `local.properties` 都不入库，release 会退回 debug 签名，**不应发布**）。
